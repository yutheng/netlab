What I learned

Describe your design: hypervisors, tenants, VNIs and addresses. Which tenants overlap, and why did you place each VM where you did?

My overlay models a small campus data centre with four hypervisors, hv1 to hv4, on the underlay 10.15.0.0/24. Two tenants represent two buildings: blocka (VNI 10100) holds the small lecture halls ccnalab and bk2, the tutorial room mm1 and the surau, and blockb (VNI 10200) holds the large lecture halls dk1 and dk2. Both tenants use 10.15.50.0/24, so their addresses overlap, ccnalab and dk1 are both .10, mm1 and dk2 are both .11, and only the VNI keeps them apart. blocka spans all four hypervisors so that flooding reaches hypervisors outside the conversation, while blockb spans only hv1 and hv3, showing that a tenant floods only to the hypervisors that host it. hv1 and hv3 each host one large and one small hall from different buildings, which balances the load and tests isolation on a shared hypervisor. dk2 shares mm1’s address on a different hypervisor, so I can check that blockb sees nothing when ccnalab pings 10.15.50.11.

Two of your VMs have the same IP address. Using your evidence, explain how a ping reaches the right one â€” and what would have to go wrong for one tenant to see another's traffic.

When ccnalab pings 10.15.50.11, its ARP request is flooded only to the other blocka VTEPs, tagged with VNI 10100, and each VTEP delivers it only into the bridge for that VNI. So only mm1 replies, even though dk2 has the same address and sits on hv3, which also receives the flood. My evidence shows this through the MAC addresses: ccnalab’s ARP entry for 10.15.50.11 is 02:00:27:74:00:0b (VNI 10100, mm1), while dk1’s entry for the same address is 02:00:27:d8:00:0b (VNI 10200, dk2), and a capture on dk2 during ccnalab’s ping recorded 0 packets. For one tenant to see another’s traffic, the separation would have to fail, for example if two tenants were given the same VNI or a VM port were added to the wrong bridge. Both VMs at 10.15.50.11 would then share one Layer-2 network, causing an IP address conflict in which ARP gets two replies and pings reach whichever VM answered last.

Using your evidence, explain what was flooded, to which hypervisors, and what each VTEP learned. With 50 hypervisors in one VNI, how many copies would one broadcast need â€” and how would EVPN change that?

When ccnalab first pinged mm1, hv1 did not yet know where mm1’s MAC was, so it flooded the ARP request to every other blocka VTEP (hv2, hv3 and hv4) using the flood list my tenant_commands() created. My capture on hv3 shows this, a VXLAN packet from 10.15.0.1 with VNI 10100 carrying “who-has 10.15.50.11”, even though hv3 was not part of the conversation. The pings themselves never reached hv3, because once mm1 replied, hv1 learned that mm1’s MAC (02:00:27:74:00:0b) is behind 10.15.0.2 and sent the rest only there. hv3 also learned something, ccnalab’s MAC (02:00:27:74:00:0a) is behind 10.15.0.1, from the flooded ARP alone. This head-end replication does not scale, because with 50 hypervisors in one VNI, every broadcast would need 49 separate copies on the underlay. EVPN removes most of this flooding by adding a BGP control plane. Each VTEP advertises its local VMs’ MAC and IP addresses in Type 2 routes, so every VTEP’s table is filled before any traffic is sent. Type 3 routes build the flood list automatically, and a VTEP can answer ARP requests locally (ARP suppression) instead of flooding them to all 49.

Compare your two MTU fixes using your measurements. Which would you choose for a data centre, what does each cost, and who has to change what?

I compared the two fixes on my black-hole design, where both tenants send up to 1500 bytes but the tunnel carries only 1450, so full-size pings were lost silently and TCP collapsed. With fix A (tenant MTU 1450, underlay 1500), a 1422-byte ping (1450 bytes) worked, 1423 was refused at the VM with “message too long, mtu=1450”, and iperf3 reached 2.34 Gbit/s. With fix B (tenants 1500, underlay 9000), 1472 worked, 1473 was refused at the VM with “mtu=1500”, and iperf3 reached 2.38 Gbit/s. Both fixes remove the black hole because the size limit is now enforced at the VM with a clear error, instead of packets disappearing in the tunnel. The throughput difference is within the noise of my runs, but fix B is slightly more efficient, since each TCP packet carries 1460 bytes of data instead of 1410 for the same 90 bytes of headers. Fix A costs every tenant 50 bytes per packet and requires each VM’s MTU to be changed, while fix B requires the operator to enable jumbo frames on every switch, router and link in the underlay, because a single device left at 1500 would bring the black hole back. I would choose fix B, because the tenants keep the standard 1500 and never need to know a tunnel exists, and the operator, who controls all the underlay hardware, only has to configure it once. This matches common practice in modern data centres, where the physical network is built with an MTU of around 9000 so that 1500-byte tenant traffic fits with room for encapsulation. Lowering the tenant MTU, as OpenStack does automatically with 1450 on a 1500 underlay, is kept for networks whose underlay the operator cannot control.

If your hypervisors' VTEPs were P4 switches running the lecture's vtep.p4, what would have to fill the vtep_encap table, and how? What would replace flood-and-learn?

A P4 switch running vtep.p4 is only a data plane: it forwards packets using the entries in its tables, but it cannot decide what those entries should be. Its vtep_encap table matches a frame’s ingress port and destination MAC, and its encap action then needs the VNI, the remote VTEP and the outgoing port, so what it really needs is which VTEP each MAC is behind. The table starts empty with a default action of drop, and unlike my Linux VTEPs, vtep.p4 has no flooding and cannot learn, because a P4 data plane cannot write its own tables. A control plane must therefore fill it through the switch’s runtime API. For example, on hv1 it would map ccnalab’s port and mm1’s MAC 02:00:27:74:00:0b to VNI 10100 and remote VTEP 10.15.0.2. For my design, that comes to 14 encap entries, plus 6 vtep_decap entries to deliver arriving frames to the right VM. A central controller could install them all in advance, because it already knows where every VM is placed: my build_overlay.py computes the same information from overlay.yaml. In a larger data centre, EVPN would supply it instead. Type 2 routes advertise each VM’s MAC and IP with the VTEP behind it, which fills vtep_encap directly and lets the VTEP answer ARP itself. Type 3 routes tell each VTEP which others share a VNI, replacing the flood list I configured by hand. Flood-and-learn is replaced by a control plane that tells every VTEP where each MAC is before any traffic is sent, so nothing has to be flooded to discover it.
